# Runtime responsibilities

Eight domain concepts own their records. A ninth, Generating, wraps calls to the AI tutor as an engine action. A tenth, Preferring, keeps each learner's tutor model and thinking level as `TutorPreferring` and each learner's home view as `ViewPreferring`. The Bun host handles everything that is not a concept's job: cookies, the Gemini connection, uploaded files, import checkpoints, and request locks. It does not sequence learning actions, and it never writes to a concept's collections. The [materials stage](stages/materials.md) lists the endpoints, reactions, views, formers, and computations that connect the concepts.

## Where the app runs

The app is deployed on 6.1040 Apps, the class platform. The platform runs one Bun process from a plain Bun image. Its file system is read-only, and each deployment starts on a fresh machine. The platform sets `HOST`, `PORT`, and `NODE_ENV`. The owner sets `PUBLIC_ORIGIN` to the app's `https` address, and the server accepts state-changing requests only from that origin. Cloudflare sits in front of the app and ends any request that takes longer than about 100 seconds.

MongoDB on the platform is a single server, not a replica set, so it has no transactions. The database name comes from `MONGODB_URI`. The server keeps at most four connections open, because the platform allows ten and the old and new versions overlap briefly during a deployment. Local development runs MongoDB the same way, so any code that needs a transaction fails on a laptop before it fails online.

Uploaded files go to the platform's S3 storage when the `S3_*` variables are set. Without them, development saves files under `.data/files`. The `/health` route answers `GET` and `HEAD` so the platform can check that the app started.

## Accounts and requests

Commons identifies the learner. The server reads the sign-in attempt and the session from HttpOnly cookies. It never trusts an owner, user ID, recovery key, or session that the browser sends in a request body.

Confirming a Commons sign-in redeems a one-time code and saves the verified identity. The next step uses that identity to find or create the local account, link it to Commons, and start a session. If the link fails, the learner can resume without registering again or redeeming another code. The server rechecks expiry after slow work and again before it sets cookies. A lost reply can leave an unused session behind until it expires, so the flow does not promise exactly one session.

Linking an account uses no transaction. A unique index on the Commons subject refuses a second link, even when two requests arrive at the same moment. After the insert, the server checks expiry again. If the sign-in expired while the insert was in flight, it removes the new link and reports the expiry.

The app runs as one process, and the host serializes work with in-process locks. One lock per sign-in attempt covers sign-in. One lock per learner covers course creation, every change to a course's skills and units, and every learning change, and it is held through AI calls so the saved context cannot change underneath a lesson. Choosing or clearing the tutor model is deliberately outside that lock, so saving a choice never waits behind a running lesson. This is safe because the tutor catalog is fixed while the server runs and only offered choices are saved; a request that is already running keeps the model and level it prepared. After an AI call, the engine checks the session again. HTTP requests and the exported runtime gateway share one admission function, which evaluates the registered formers under the learner lock, so a refused command is explained before any AI work starts. The engine and gateway give each request at most 90 seconds, and a single Gemini call made during a request gets at most 80 seconds, including any Files API uploads it needs, which keeps both under Cloudflare's limit. The upload route has its own budget of 85 seconds. The transcription worker runs outside requests and has its own, longer limits. Queries are not cached.

Native integrations use the exported runtime gateway, which keeps the same admission checks and locks as HTTP. The raw assembled invoker is an internal interface that assumes those checks already happened. The [advisory review](advisory-review.md) explains why the gateway carries this protection. Locks wait only for work the engine has already dispatched, so a queued native call cannot keep an HTTP call from releasing a lock.

A refused request reaches the browser with the sentence its design gives, not only its code. The engine keeps only the code of a refusal, so the host records that code while the request runs and, when the answer is a refusal, adds the matching sentence as `detail` from a map built from each concept's specification and the compositions' designs. Two codes keep their sentence to the endpoints whose design gives it: a missing course is explained only on the planning endpoints, and a missing skill only on the estimate adjustment. An admission refusal, a recorded tutor failure, and the tutor-choice refusals already carry their own sentences, and those win. The native gateway adds the same sentence beside the code. A few codes have no design sentence yet and arrive with their category alone; the browser then shows its general message for that category.

## Safe writes without transactions

Each concept enforces its own rules. Without transactions, a concept that changes more than one record writes them one at a time, in an order where a reader never sees a half-finished change. If a process stops partway, repeating the same request either finishes the work or is refused.

SkillMapping follows these rules:

- **Proposing a skill.** The concept first saves a pending receipt under the learner's proposal key. The receipt holds the original input and the IDs chosen for the new skill and its first version. Next it saves the version, then the skill, and finally marks the receipt as saved. A skill therefore never exists without its version. If the process stops before the end, retrying the same key finishes the save. Retrying with different input is refused.
- **Revising a skill.** The concept saves the new version first. Then it makes that version current with a single conditional update, which succeeds only if nothing else changed the skill in the meantime. If that update fails, the old version stays current, and the unused version is removed.
- **Discarding a draft.** The concept removes the skill before its versions and keeps the receipt. Replaying the original proposal after a discard is refused, so a discarded draft cannot come back.
- **Confirming, editing details, and attaching material.** Each is one conditional update on the skill. If another change got there first, the concept reads again and either retries or refuses.
- **Prerequisites, archiving, and restoring.** These rules involve two skills at once. For example, a cycle needs both A→B and B→A, and an active skill must not require an archived one. A condition on one skill cannot see a change to the other. So these actions briefly claim the course record, run their checks, make one update, and release the claim. The claim expires after 10 seconds, so a stopped process cannot lock a course for long.

The browser stores pending draft requests before it sends them and removes each one only after the server acknowledges it. The [course flows](compositions/Courses.md) describe these requests.

The other concepts keep related data in one document, so a single write is enough. AssessmentReviewing stores a case and its append-only judgments together. StudyPlanning stores a learner's plans together, which makes replacing a plan and the one-activity-at-a-time rule a single write. MasteryEstimating keeps one effective input per piece of evidence and accepts a replacement only when its revision number is higher.

## The AI tutor (Gemini)

The host calls Google's Gemini API directly. The API key lives only in the server's environment. It is sent in a request header and never appears in a URL, a log, or a response to the browser. Each learner chooses the model and its thinking level from the server's tutor catalog. A learner with no choice gets the model named by `GEMINI_MODEL`, or `gemini-3.8-flash` when it is unset, at that model's default level. The deployed `GEMINI_MODEL` must be unset or one of the catalog's offered names; otherwise the server stops at startup. Dictation always uses the configured model. The [tutor settings](compositions/Settings.md) describe the catalog and its checks.

Each request sends the tutor's instructions, the learner's request, and the selected course material. Text renditions and recording transcripts go as text. Original PDFs and images, including HEIC and HEIF photos, go inline when each is 15 MB or less and the request's inline files stay within 30 MB, and otherwise by Files API reference. One request carries at most 40 images. The host keeps each Files API reference in its own collection and uploads the file again when less than one hour remains of Gemini's 48-hour copy. If a file cannot be sent, the request fails with a plain explanation rather than leaving the file out. Graded-work extraction is stricter: every original PDF and photo goes inline in full, and one larger than 15 MB refuses the request before Gemini is contacted. Gemini returns JSON that matches a schema, and the host still checks the answer and every cited material and location before anything is saved.

When Gemini fails, the learner sees a plain explanation instead of a generic error. The host tells apart a busy service, a used-up quota or billing problem, a missing or wrong key, a chosen model that Google cannot find or that has used up its own quota, a thinking level the model refuses, a request Gemini would not accept, a safety block, an answer that was too long or empty or badly formed, a timeout, a network failure, a course file that could not be sent or whose copy had expired, files too large for the model, and a file the model could not read. A refusal is blamed on the chosen model only when Google's response names that model, and dictation keeps its current sentences. The server log records Google's status and message, which help the app owner fix setup problems. If the server has no key, the AI buttons are disabled and the reason appears beside them, and recordings and videos cannot be imported.

Dictation sends the learner's recording to Gemini, which writes down exactly what was said, with spoken math written as symbols. The dictation route accepts a body of at most 16 MB, a recording of up to 15 MB plus the rest of its form, and stops reading a larger body as soon as it passes that size. The recording is not stored. The transcript is saved only if the learner sends it as an answer.

Course materials and answers leave the app when they go to Google. The setup screen says so, and it asks learners not to upload anything private.

## File import

`MaterialImportStore` saves each import request with a server-generated key and the exact prepared input. Its [contract](material-import-store.md) defines the CREATED, SOURCES_SAVED, TRANSCRIBING, READY, COMPLETE, and DISCARDED checkpoints. Unique owner/request and owner/key indexes protect retries, and the store is written outside reaction conditions.

The upload endpoint checks the session and the course-access former, hashes the bytes it actually received, and saves the originals under paths specific to the owner. It then reads documents, records what it could not read, and saves READY before calling `GroundedTutoring.addMaterial`. An import that contains a recording or video saves TRANSCRIBING instead and answers at once. A transcription worker in the same process sends each recording to Gemini, one at a time and outside any HTTP request, and saves each transcript in the import store. The learner's next request that lists imports saves the material. A worker's claim on a recording ends five minutes after its last renewal, so a restart resumes the work. Each turn of the worker also saves READY for any import whose transcripts are all saved, and finishes deleting the files of removed imports, so neither step depends on the process that started it. An exact retry reuses the saved key and input. The material action stores its record and its retry mapping together, so a restart after that save but before COMPLETE recovers the same material.

The importer runs in memory with TypeScript. It reads PDF text page by page, plain text, Markdown, and code, notebooks cell by cell, and the text of Word, PowerPoint, and Excel files. It keeps PNG, JPEG, WebP, HEIC, and HEIF images as images. It does not render pages as images; a page without text becomes a page location that the tutor reads from the original PDF. For a recording or video, it reads only the header and timestamps, to learn the type and length. Office files carry a note that their pictures and charts were not included. [Material data](material-data.md) lists the formats and their source locations.

Uploads allow 12 files and 95 MB in total, where 1 MB is 1,048,576 bytes. Each PDF or presentation allows 50 pages, and each recording or video allows 2 hours. Office files may unpack to at most 50 MB. ZIP archives, older Office formats, and other unsupported types are refused before anything is saved. Learners can still open their original files, play their recordings, and see what the importer could not read. The importer does not promise to read every layout correctly, and transcripts can contain mistakes. The interface now offers importing any material the tutor model can read; the [material flows](compositions/Materials.md) describe uploads, unfinished imports, and how each kind is viewed.

A download goes through the declared material-read endpoint, which checks the owner and course access, and then requires an exact saved file reference. Knowing a file ID is not enough to download it.

## Lessons, practice, and evidence

Declared views join the learner's skills, their current requirements, and the source material before a Generating action asks the tutor. The host checks the returned text and its citations. A citation of the learner's own attached work is dropped, since that work is sent to be read and is not a course material; an answer that cites nothing else is refused with a sentence the learner can act on. The endpoint then rechecks the skill's definition, and if the definition changed during generation, it reports a conflict instead of saving content under the new requirements. Existing sessions keep their original requirements and sources. A submitted photo is read as the learner's own work, separately from any reference solution.

Practice checks whether prerequisites are ready. Lesson explanations stay available even when prerequisites need work. A hint is recorded before it is shown, and a recorded hint or declared outside help rules out an independent-success judgment.

Submitting work requires the learner to review the whole attempt and confirms the number of dialogue turns shown. GroundedTutoring saves the freshness and outside-help declarations with that review. The reviewed work is built from the saved responses, corrected transcripts, attachments, hints, citations, and fixed criteria, and it uses the server's time. The browser cannot replace the criteria, owner, result, or recorded help. The learner states whether the exact problems were unfamiliar, and work of uncertain freshness cannot meet the full gate.

A submission reaction saves the assessment case, and that save triggers closing the task. These are separate durable actions, and every later change checks whether a case already exists. If the AI fails, the case stays available to retry. A regrade adds a judgment and keeps earlier judgments and the original work. A manual correction follows the same help, freshness, and gate rules.

Successful assessments and revisions trigger evidence reactions. Each one reads the effective judgment and applies it once to the skill's mastery track. A higher revision replaces the earlier contribution instead of counting as another success. When a learner signs in and reads their courses, repair reactions recover any task closures and mastery contributions that a failure left behind, using the durable records. The read waits for those repairs. Unjudged cases stay visibly pending. If a later step fails, earlier concept writes stay saved, and a fresh read and plan request recover the rest.

## Review planning

Study dates use the `America/New_York` time zone, and mastery decay uses elapsed time. A declared pure computation proposes candidate activities and a digest of the context from query snapshots. Before activating a plan, StudyPlanning also compares its own saved budget, date, and work records.

The planner proposes ten-minute activities across seven days. The first independent success suggests a review the next day. Independent work on later days stretches the gap to three days and then seven. A slip or a gap in understanding resets it. Candidate keys stay the same while the same work and window still apply. The plan also shows work that does not fit.

Changes to the budget, an exam, confidence, effective evidence, a manual adjustment, or an activity's outcome (finished, stopped, or missed) request a new plan. A separate reaction activates the proposal only after the concept and context checks pass. Refreshing waits while an activity is in progress. Starting an activity checks its current requirements and prerequisites. Finishing a timed activity records the actual time but does not create assessment evidence, and a missed activity does not change mastery directly.

Learners record exam dates for a course in the planner. Preparation for the nearest exam then comes first, and when it cannot all fit before the exam, the plan lists the work it would leave out and changes only after the learner confirms. The [planning flows](compositions/Planning.md) describe exams and these tradeoffs. The app does not yet suggest a reference source for a learner who has no material.

## Frontend boundary

Vue uses the generated HTTP client and output types for courses, suggestions, tutoring, assessment, mastery, and planning. A small host transport handles the AI status check, multipart uploads, unfinished imports, file downloads and playback, and microphone recordings. Browser types leave out the private `/internal/*` routes. The upload answers either a material identity, whose type comes from the private generated material endpoint, or an unfinished import's request ID and state, whose type the host transport declares.

The frontend shows state and sends the learner's choices. It does not calculate mastery, copy the effects of a judgment, allocate review work, or decide who owns a record. A single generated question command saves the learner's question and asks for the lesson reply. If the AI fails after the question was saved, the interface offers a separate retry.

## Verification boundary

The tests use a real, standalone MongoDB server for concept storage and controlled AI responses for integration. The file tests run the real parsers on small PDF, Word, PowerPoint, and Excel fixtures, and on a scanned PDF, a HEIC photo, a short WAV recording, and a tiny MP4 video. The storage tests use both the disk store and a fake S3 server. The Gemini tests use a fake `fetch` to check the request format, Files API uploads, transcription, parsing, and every error path. An isolated browser test uses canned AI responses. These tests do not establish how accurately the tutor grades work, reads handwriting, or transcribes recordings. [P3 status](../P3.md) records the checks made on the deployed app.
