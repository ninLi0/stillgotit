# Progress reactions

These reactions carry a learner's finished work into the rest of the application. A confirmed practice attempt becomes an assessment case, each saved judgment becomes evidence on the matching mastery track, and new evidence, a new budget, a restored course, or the end of an activity asks the planning concept for fresh reviews. Each paragraph below states one reaction as a single rule. The "when" part names the action that triggers it, the "where" part names each condition together with the view, query, or computation that checks it, and the "then" part names the action the reaction calls and the arguments it passes. The sentences after each rule explain why it works that way.

## Submitting practice work

[SubmitReviewed](reaction:Progress.SubmitReviewed): when `GroundedTutoring.confirmAttempt` succeeds for a learner and a practice task with the learner's `unseen` and `outsideHelp` declarations, where [OpenSession](view:Reads.OpenSession) shows that the task is still the learner's open session and gives its skill and requirements version, `GroundedTutoring._review` reports the task as ready, `MasteryEstimating._track` finds the learner's track for that skill and version, `GroundedTutoring._task` gives the saved question and criteria, `GroundedTutoring._sessionData` gives the saved session, the flow's current instant gives the attempt time, and [submissionInput](computation:submissionInput) turns the saved session and the two declarations into the response, its source key, the help received, and the freshness, then call `AssessmentReviewing.submit` with the learner as author, the skill as subject, the requirements version, the source key, the task, the question, the criteria, the response, the help, the freshness, and the attempt time as `performedAt`.

The learner confirms the whole attempt only after reviewing it and declaring whether the problems were new to them and whether they had outside help. A task is ready when it is open, has at least one learner answer, and has no voice answer whose transcript is still unchecked. OpenSession also excludes a task that already has a submitted case, so confirming the same attempt twice cannot submit it twice. The submitted case is immutable. It keeps the requirements version that the task was written for, even if the skill has been revised since, and its date is the server's time rather than a time sent by the browser.

[CloseSubmitted](reaction:Progress.CloseSubmitted): when `AssessmentReviewing.submit` succeeds for an author and a task, where `GroundedTutoring._session` shows that task as an OPEN session owned by that author, then call `GroundedTutoring.close` with the author as owner and the task as the session.

The task closes as soon as its case is saved, before the provider grades the work. A failed provider request therefore leaves the original work saved in the case and available for retry.

## Applying judgments to mastery

[AssessedEvidence](reaction:Progress.AssessedEvidence): when `AssessmentReviewing.assess` succeeds for a case, where `AssessmentReviewing._case` gives the case's author, [NeedsEvidence](view:Reads.NeedsEvidence) holds for that author and case and gives the case's skill, requirements version, freshness, and attempt date together with the effective judgment's revision, result, `gateMet`, rationale, and origin, and [evidenceAttribution](computation:evidenceAttribution) builds an attribution from that origin and rationale, then call `MasteryEstimating.acceptEvidence` with the author as learner, the skill as subject, the requirements version, the case as evidence, the revision, the attempt date as `performedAt`, the result as `signal`, the freshness, `gateMet`, and the attribution.

AssessedEvidence reads the author from the case because `assess` names only the case.

[RevisedEvidence](reaction:Progress.RevisedEvidence): when `AssessmentReviewing.revise` succeeds for an author and a case, where NeedsEvidence holds for that author and case and evidenceAttribution builds the attribution, then call `MasteryEstimating.acceptEvidence` with the same arguments that AssessedEvidence passes.

[ImportedEvidence](reaction:Progress.ImportedEvidence): when `AssessmentReviewing.importGraded` succeeds for an author and answers with the new case, where NeedsEvidence holds for that author and case and evidenceAttribution builds the attribution, then call `MasteryEstimating.acceptEvidence` with the same arguments that AssessedEvidence passes.

These three reactions apply a judgment as soon as it is saved, whether it comes from the tutor's assessment, a regrade or correction, or imported graded work. Each one reads the effective revision, which is the case's newest judgment, and the case's original attempt date rather than the time of grading. NeedsEvidence holds only when the learner has a mastery track for the case's skill and requirements version, and that track has no contribution from this case yet or has one from an older revision. A regrade therefore replaces the case's one contribution; it does not count as another attempt.

[InitializedEvidence](reaction:Progress.InitializedEvidence): when `MasteryEstimating.initialize` succeeds for a learner, a skill, and a requirements version, where `AssessmentReviewing._cases` gives one of the learner's cases for that skill, NeedsEvidence holds for that case and gives the same requirements version that was just initialized, and evidenceAttribution builds the attribution, then call `MasteryEstimating.acceptEvidence` with the same arguments that AssessedEvidence passes, once for each case that meets these conditions.

`AssessmentReviewing._cases` lists the learner's cases for every requirements version of the skill, so the match on the initialized version is what limits this reaction to the new track. Evidence for an earlier definition does not silently certify a newer one. The reaction exists for a case that was judged before the learner set a starting estimate, such as imported graded work. With no track, NeedsEvidence did not hold for that case, so its judgment waited until now.

After a skill definition is revised, the new version's mastery track starts from the previous estimate, and is repaired on the next course read, by two reactions declared in [Courses](Courses.md): RevisedTrack and RepairRevisedTrack. They live there because the course-editing flow owns the learner's lock and the course read.

## Proposing new reviews

Every reaction in this section reads three shared views. [PlanContext](view:Reads.PlanContext) computes four values from the course map, the learner's progress, and the course's planning schedule. They are the review candidates, the horizon end, an explanation, and the basis, which is a fingerprint of the current evidence, manual adjustments, and requirements. [CanReplan](view:Reads.CanReplan) holds when the learner owns the course, has saved a study budget for it, and has no activity in progress in it. [ActivityInProgress](view:Planning.ActivityInProgress) holds when the learner has an activity in progress in any of their courses. The planning concept refuses a replan while any course of the learner has an activity in progress, so a replan is never attempted then. Each reaction below requires that ActivityInProgress does not hold, and not only CanReplan, which looks at one course. Without that condition, a change in one course during an activity in another would ask for a replan that the concept refuses, and the refusal would become the answer to the learner's change even though the change was saved.

[ReplanAfterEvidence](reaction:Progress.ReplanAfterEvidence): when `MasteryEstimating.acceptEvidence` succeeds for a learner and a skill, and the ordinary work in that causal flow has settled, where [OwnedSkill](view:Reads.OwnedSkill) gives the skill's course, CanReplan holds for the learner and that course, ActivityInProgress does not hold for the learner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the learner, the course as scope, the candidates, the horizon end, the basis, the explanation, and `workloadComplete` false.

[ReplanAfterConfidence](reaction:Progress.ReplanAfterConfidence): when `MasteryEstimating.initialize` succeeds for a learner and a skill, and the ordinary work in that causal flow has settled, where OwnedSkill gives the skill's course, CanReplan holds for the learner and that course, ActivityInProgress does not hold for the learner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the learner, the course as scope, those four values, and `workloadComplete` false.

Both reactions wait for their flow to settle, so that the proposal is built from the requirements and evidence as they stand after the rest of the flow's work is done. After a new track, for example, InitializedEvidence may first add contributions from cases judged earlier, and the proposal should reflect them. No proposal is made while an activity is in progress; ReplanAfterFinish and ReplanAfterStop make one when the activity ends.

[ReplanAfterBudget](reaction:Progress.ReplanAfterBudget): when `StudyPlanning.configure` succeeds for a learner and a course, where CanReplan holds for them, ActivityInProgress does not hold for the learner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the learner, the course as scope, those four values, and `workloadComplete` false.

A new budget changes how much work fits into each day, so the course's reviews are proposed again from the changed preferences.

[ReplanAfterRestore](reaction:Progress.ReplanAfterRestore): when `SkillMapping.restoreCourse` succeeds for an owner and a course, where CanReplan holds for them, ActivityInProgress does not hold for the owner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the owner as learner, the course as scope, those four values, and `workloadComplete` false.

An archived course's plan can fall behind while it is set aside, because days pass and finishing or stopping an activity elsewhere leaves it alone, so restoring the course proposes its reviews again from the current date and evidence.

[ActivateRoutine](reaction:Progress.ActivateRoutine): when `StudyPlanning.replan` succeeds with `workloadComplete` false for a learner and a course and answers with a plan, where PlanContext gives the course's current basis and `StudyPlanning._proposalCheck` for that plan and basis reports `canActivate` true and `needsConfirmation` false, then call `StudyPlanning.activateRoutine` with the learner, the plan, and the current basis.

ActivateRoutine checks both the planning concept's state and the current application fingerprint before activating a routine proposal. `canActivate` is true only when the plan's saved local inputs still match the concept's current ones, its basis equals the current basis, and the learner has no activity in progress. A proposal needing tradeoff approval cannot use this path. It stays PROPOSED until the learner confirms or declines it, as the [planning flows](Planning.md) describe. Every replan in the application passes `workloadComplete` false, so this reaction also follows the Propose endpoint, the exam reactions in the planning flows, and ReplanAfterAdjustment in the [learning flows](Learning.md).

## After an activity ends or is missed

[ReplanAfterFinish](reaction:Progress.ReplanAfterFinish): when `StudyPlanning.finish` succeeds for a learner, where `SkillMapping._courses` gives one of the learner's courses with status `ACTIVE`, CanReplan holds for the learner and that course, ActivityInProgress does not hold for the learner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the learner, the course as scope, those four values, and `workloadComplete` false, once for each course that meets these conditions.

[ReplanAfterStop](reaction:Progress.ReplanAfterStop): when `StudyPlanning.stop` succeeds for a learner, where `SkillMapping._courses` gives one of the learner's courses with status `ACTIVE`, CanReplan holds for the learner and that course, ActivityInProgress does not hold for the learner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the learner, the course as scope, those four values, and `workloadComplete` false, once for each course that meets these conditions.

Finishing or stopping an activity refreshes every active course with saved preferences, not only the activity's course. It skips an archived course: the learner has set that course aside and the page no longer opens it, so a fresh proposal there would serve no one, and its plan stays as it was until ReplanAfterRestore refreshes it when the course is restored, as the [course flows](Courses.md) describe. No course can be replanned while an activity is in progress, so an exam, budget, missed activity, new evidence, or adjustment in another course during the activity takes effect here. The activity has ended by the time these two reactions run, so ActivityInProgress does not hold then. They state the condition anyway, so that every replan in this section follows the same rule.

[ReplanAfterMiss](reaction:Progress.ReplanAfterMiss): when `StudyPlanning.miss` succeeds for a learner and an item, where `StudyPlanning._item` gives the item's learner and course, CanReplan holds for them, ActivityInProgress does not hold for the learner, and PlanContext gives the four values for that course, then call `StudyPlanning.replan` with the learner, the course as scope, those four values, and `workloadComplete` false.

ReplanAfterMiss refreshes only the missed activity's course. A missed activity was never in progress, so no other course was waiting for it to end. None of these three reactions changes mastery. A missed activity is not assessment evidence, and finishing an activity's timer does not prove mastery either.

## Repairs on the skill read

[RepairReadEvidence](reaction:Progress.RepairReadEvidence): when `Sessioning.use` returns the learner's identity inside the Learning.Read endpoint, where [sessionSubject](computation:sessionSubject) gives the learner from that identity, `SkillMapping._courses`, `SkillMapping._units`, and `SkillMapping._skills` give a skill in a unit of one of the learner's courses, `AssessmentReviewing._cases` gives one of the learner's cases for that skill, NeedsEvidence holds for that case, and evidenceAttribution builds the attribution, then call `MasteryEstimating.acceptEvidence` with the same arguments that AssessedEvidence passes, once for each case that meets these conditions.

[RepairReadClosure](reaction:Progress.RepairReadClosure): when `Sessioning.use` returns the learner's identity inside the Learning.Read endpoint, where sessionSubject gives the learner, the same three SkillMapping queries give a skill in one of the learner's courses, `AssessmentReviewing._cases` gives one of the learner's cases for that skill, `AssessmentReviewing._case` gives that case's task, and `GroundedTutoring._session` shows the task as an OPEN session owned by the learner, then call `GroundedTutoring.close` with the learner as owner and the task as the session, once for each task that meets these conditions.

These two reactions repair a missing contribution or an unclosed submitted task from durable concept records, for example after the process stopped between saving a case and applying its judgment. They watch only the successful authentication step of Learning.Read, and they inspect only that learner's courses and cases. The read endpoint waits for this causal work before returning. Repeated reads do not add another contribution or judgment, because NeedsEvidence no longer holds once the contribution exists and a closed task is no longer OPEN. This is explicit recovery; the framework does not replay old occurrence logs after restart.
