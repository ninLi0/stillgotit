# Learning flows

The frontend sends learner choices through the generated client. The session cookie supplies identity. Each flow reads owned state through declared views. Generated answers enter through Generating actions. File access and provider transport receive prepared values and cannot sequence domain actions.

[Read](reaction:Learning.Read) returns saved study data through the skill former. It binds one instant for the request and reads the estimate's explanation at that instant, as described in the [shared reads](LearningReads.md). [Progress](reaction:Learning.Progress) returns estimates for the owned course. Progress changes nothing, so the host answers it without the learner's lock, even while one of the learner's tutor requests holds it. Read keeps the lock, because its flow runs the repairs in the [progress reactions](Progress.md), which can save records; the [runtime responsibilities](../runtime.md) explain the difference. [Confidence](reaction:Learning.Confidence) creates one provisional track for the current requirements or returns the existing track. It never overwrites prior practice.

[Lesson](reaction:Learning.Lesson) joins the skill to its owned sources and saves the lesson with the learner's request at once, before any tutor work, as described under "Starting a lesson" below. [Task](reaction:Learning.Task) requests a practice task, rechecks the session and the original requirements, and saves the task; it also requires a mastery track and ready prerequisites. When the skill is not one of the learner's confirmed skills, both answer `SKILL_UNAVAILABLE` before any other step. Task requests the complete demonstration gate and rejects a repeated question. The provider does not assign a mastery score.

GroundedTutoring checks only the shape of a session's sources, so these flows guarantee the rest. Lesson and Task read the learner's materials in the skill's course with `Library._sourceSet`, and [selectSources](computation:selectSources) selects the skill's sources from among them. Question, Reply, Hint, and the assessment flows select the session's saved materials the same way. The tutor is sent only the selected sources, and the host accepts a tutor answer only when each citation names one of them and a location in it, so a saved lesson, task, or answer never names another learner's material or a material from another course. `Library._sourceSet` answers only materials whose purpose is SOURCE. The learner's own work, such as a photo attached to an answer, is never among them, so no lesson, task, tutor answer, hint, or skill suggestion selects it or is taught from it, as the [course composition](Courses.md#the-learners-own-work) describes. The tutor reads that work only as the attempt it belongs to, as described under "Several attachments in one response" below.

A material the learner deleted, as the [course composition](Courses.md#deleting-a-material) describes, is no longer among their sources, so selectSources leaves it out. Lessons, practice, tutor answers, and hints use the sources that remain, and a new lesson or task is saved with only those. Each needs at least one: when none remains, [request admission](LearningAccess.md#deleted-sources) declines the request with a sentence that says the material was deleted and what to do. Grading needs no source, because it judges the saved work against the criteria saved with the task, so Assess, RetryAssessment, and Regrade grade an attempt even when every material of its task was deleted. A deleted material's text never reaches the tutor again. Past sessions keep their explanations, dialogue, and citations unchanged.

[Respond](reaction:Learning.Respond) checks the current dialogue length, open session, and the ownership of every attachment before saving learner work. [Question](reaction:Learning.Question) saves a lesson question and requests its answer in one flow. [Reply](reaction:Learning.Reply) requests what an open lesson is waiting for: the opening explanation of a lesson saved without one, or the answer to an unanswered saved lesson question. [Hint](reaction:Learning.Hint) records requested help before contacting the provider, so a failed hint request cannot later be treated as independent work. [Transcript](reaction:Learning.Transcript) records corrections to an existing voice response. When the session is not one of the learner's open sessions, each of these five endpoints answers `SESSION_UNAVAILABLE` and changes nothing. Request admission declines such a request first, so over HTTP the learner sees the admission detail instead, as the [request admission](LearningAccess.md) describes.

## Starting a lesson

A lesson is saved from the learner's request before the tutor writes anything, so a slow tutor, a failed tutor call, or a learner who leaves the page while the tutor works never loses the request. [Lesson](reaction:Learning.Lesson) takes `skill` and `request`.

- When the request arrives, `Sessioning.use` turns the session into the acting learner. No request field can name another learner.
- Where [ActiveSkill](view:Reads.ActiveSkill) does not hold, the endpoint answers `SKILL_UNAVAILABLE` and changes nothing.
- Where ActiveSkill gives the skill's current definition, [SkillContext](view:Reads.SkillContext) gives its context and the learner's sources in its course, and selectSources finds at least one material of the skill among those sources, the endpoint calls `GroundedTutoring.requestLesson` with the learner as owner, the skill as topic, that definition, the request, and the skill's materials that remain. It answers `{ lesson }` at once. No tutor is asked, so the answer carries no `tutor`.

The new lesson is unexplained: its explanation and opening citations are empty, and the concept refuses learner questions in it until the opening explanation is saved, so Question and Respond refuse it too. Read, Recent, and Continue list it like any other lesson, titled by its request.

The page then asks [Reply](reaction:Learning.Reply) for the opening explanation:

- When the request arrives, `Sessioning.use` turns the session into the acting learner. Where [OpenSession](view:Reads.OpenSession) does not hold, Reply answers `SESSION_UNAVAILABLE` and changes nothing.
- Where [SessionSources](view:Reads.SessionSources) gives the open lesson and the learner's sources in its course, [lessonUnexplained](computation:lessonUnexplained) holds for it, `GroundedTutoring._lesson` gives its request, SkillContext gives the current context of its skill, and selectSources finds at least one material saved with the lesson among those sources, [lessonRequest](computation:lessonRequest) prepares the opening request from the skill's title and outcome, the learner's request, and the lesson's sources that remain. The learner's answer style is added, as [Interactive examples](#interactive-examples) describes, then the tutor choice, and `TutorGenerating.generate` asks the tutor.
- After the tutor answers, `Sessioning.use` checks the session again. Where OpenSession still holds and the lesson, read again, is still unexplained, Reply calls `GroundedTutoring.explainLesson` with the answer's text and citations and answers `{ tutor }`. Where OpenSession no longer holds, it answers `SESSION_CHANGED` and saves nothing.

When the tutor fails, the lesson stays saved and unexplained, with its request. The learner sees the failure's reason, and the page shows "Retry tutor reply" where the explanation would be. The retry is another Reply, which asks for the opening again. The opening uses the skill's context at the time of that Reply, and the lesson keeps the requirements version it was saved with; a lesson is never assessed, so no answer is discarded because the requirements changed meanwhile.

Reply's other case is the one it always had: where [hasLessonQuestion](computation:hasLessonQuestion) holds, it asks the tutor to answer the latest learner question and records the answer with `GroundedTutoring.answerLesson`. The two cases never hold together, because an unexplained lesson has no dialogue. After the tutor answers, Reply reads the lesson again and records the answer as what it was asked for; the learner lock keeps the lesson unchanged meanwhile. A lesson that waits for neither, because it is explained and its latest turn is the tutor's, gets no tutor request: request admission declines Reply first with the sentence of [ReplyReady](former:Access.ReplyReady), "Send a question in an open lesson before asking for a reply."

## Several attachments in one response

Respond and Question take `attachments`, a list of material identities, in place of the single `attachment`. The list is required and may be empty. Each entry is one of the learner's own materials in the session's course: usually a photo of paper work uploaded for this answer, which is saved as their work, or one of their sources. The rule for each entry is the rule that applied to the single attachment:

- When either request arrives, `Sessioning.use` turns the session into the acting learner.
- Where the session is the learner's open session (an open lesson for Question), the displayed dialogue length is current, and [responseInput](computation:responseInput) finds every listed material among the learner's own sources and work in the session's course, both of which [SessionSources](view:Reads.SessionSources) reads, the endpoint calls `GroundedTutoring.respond` once. That call saves the text and the retained files of all listed materials as one learner turn, in the order the learner attached them.
- Where any listed material is unknown, belongs to another learner, or belongs to another course, or the same material is listed twice, or the response has neither text nor an attachment, nothing is saved. Request admission declines the whole response before dispatch, as it does today, with the admission layer's decline code and one detail per endpoint. For Respond the detail is "Choose an open session, check the latest dialogue, and attach only your own work from this course, each file once." For Question it is "Choose an open lesson, check the latest dialogue, and attach only your own work from this course, each file once."

The detail does not name the attachment that failed. The page lists only files it uploaded to this skill's course for this answer, so it cannot send an attachment that fails this check; the check guards against altered requests. After a refusal the page keeps the draft and every attachment, so the learner can remove one and send again.

Respond answers after the turn is saved. Question then requests the tutor's answer from the saved dialogue, so the provider receives every attached file as the learner's submitted work, apart from the sources it teaches from. Assessment later uses all files saved in the learner's responses, sent to the grader the same way. Removing a photo before sending only changes the list the screen sends; nothing is saved until the learner sends.

## Finishing a lesson

A practice task closes when its attempt is submitted, as CloseSubmitted in the [progress reactions](Progress.md) describes. A lesson has no submission, so the learner says when it is finished. [FinishLesson](reaction:Learning.FinishLesson) takes `studySession`.

- When the request arrives, `Sessioning.use` turns the session into the acting learner. No request field can name another learner.
- Where [OpenSession](view:Reads.OpenSession) holds for that learner and session, and `GroundedTutoring._lesson` finds the session as a lesson, the endpoint calls `GroundedTutoring.close` with the learner as owner and the session, and answers `{}`.
- Where OpenSession holds but `GroundedTutoring._lesson` finds no lesson, the session is an open practice task. The endpoint answers `SESSION_UNAVAILABLE` and changes nothing, because a task closes only when its attempt is submitted.
- Where OpenSession does not hold, because the session is unknown, belongs to another learner, or is already closed, the endpoint answers `SESSION_UNAVAILABLE` and changes nothing. A second request to finish the same lesson gets this answer.

No public code says "this is a practice task", so request admission does the explaining: it declines both refusal cases first, with the sentence of [FinishReady](former:Access.FinishReady), as the [request admission](LearningAccess.md) describes.

A finished lesson keeps its request, explanation, and dialogue, and Read still returns it with status CLOSED. Respond, Question, Reply, and Transcript refuse it, because OpenSession no longer holds, and [Continue](reaction:Reads.Continue) no longer lists it. The learner can start a new lesson, or continue this one as the next section describes. No reaction is triggered by `GroundedTutoring.close`. CloseSubmitted and RepairReadClosure call it only for a task with a submitted case, which a lesson never has, so finishing a lesson changes no case, estimate, or plan.

## Continuing a finished lesson

A learner who finished a lesson and then thinks of another question can continue the same lesson, so the question is answered in the conversation that already holds the lesson's sources and earlier answers, instead of in a new one that starts over. [ReopenLesson](reaction:Learning.ReopenLesson) takes `studySession`.

- When the request arrives, `Sessioning.use` turns the session into the acting learner. No request field can name another learner.
- Where [ReopenableLesson](view:Reads.ReopenableLesson) holds for that learner and session, the endpoint calls `GroundedTutoring.reopenLesson` with the learner as owner and the session as the lesson, and answers `{}`. ReopenableLesson holds for the learner's own lesson whose status is CLOSED and that is not archived.
- Where ReopenableLesson does not hold, the endpoint answers `SESSION_UNAVAILABLE` and changes nothing. This covers an unknown session, another learner's session, a lesson that is still open, a practice task, and an archived lesson. A second request to reopen the same lesson gets this answer, because the lesson is open by then.

Request admission declines each of these cases first, with the sentence of [ReopenReady](former:Access.ReopenReady), as the [request admission](LearningAccess.md) describes.

Reopening changes only the lesson's status. The lesson keeps its request, its opening explanation and citations, its dialogue, and the requirements version and sources it was saved with, so the tutor answers the next question from the same sources as before. A source the learner deleted since then stays left out, as it is for any open lesson. Once the lesson is open, OpenSession holds for it again, so Question, Reply, Respond, Transcript, and FinishLesson accept it, Continue lists it, and the sidebar shows it as open. A lesson can be finished and continued again any number of times.

A practice task never reopens. It closes when its attempt is submitted, and that attempt is the work its assessment judged, so adding to it afterwards would change evidence that has already counted. The learner starts a fresh check instead.

An archived lesson is not reopened while it is archived, because archiving keeps a conversation read-only, as "Archiving a conversation" below describes. The learner restores it first and then continues it, so the lesson page offers "Restore conversation" for an archived finished lesson, not "Continue this lesson".

Nothing outside GroundedTutoring changes. No reaction is triggered by `GroundedTutoring.reopenLesson`, and no reaction or view in the progress and planning flows keys on a lesson's status. CloseSubmitted and RepairReadClosure in the [progress reactions](Progress.md) act only on a practice task with a submitted case, which a lesson never has. The plan's activity in progress is StudyPlanning's own record of an activity the learner started from the plan, read with `StudyPlanning._next`, and a lesson's status does not touch it. Like finishing, reopening therefore changes no case, estimate, or plan.

On the lesson page, a finished lesson that is not archived shows, where the message box was, "This lesson is finished. You can continue it with another question here, or start a new conversation." with "Continue this lesson" as the main action and "Keep learning" beside it. Continue calls ReopenLesson. When it succeeds, the page reads the skill again, the message box returns with the keyboard focus in it, and the sidebar and Home's Continue card read again, so they show the lesson as open. A refusal shows the server's sentence in the page's message area, and the lesson stays finished. A refusal usually means the lesson changed in another tab, for example it was archived or already continued there, so the page reads the skill again and the sidebar reads its lists again, and the two agree. ReopenLesson needs no tutor source, so the server reopens a finished lesson whose every material has been deleted, but the tutor could not answer a question in it. The page therefore does not offer Continue for such a lesson, and says instead: "This lesson is finished, and the materials it was grounded in have been deleted, so the tutor can no longer answer in it. Start a new conversation to keep going."

## Archiving a conversation

The sidebar lists every conversation in the course, so after a few weeks it fills with lessons and practice the learner is done with. Archiving puts a conversation away: it leaves the sidebar and Home's Continue card and waits under "Archived conversations", at the end of the sidebar's Conversations group, until the learner restores it.

**The rule for open conversations.** Archiving puts a conversation away exactly as it is, whether it is open or finished, a lesson or practice. It finishes nothing and submits nothing. While a conversation is archived, it is read-only: it opens from the archived list to be read, but nothing can be added to it. Restoring it puts it back exactly as it was, so an open lesson or practice task can be continued once it is restored, and a finished lesson can then be reopened. Archive and Restore therefore undo each other, which is the simplest rule a learner can hold: archiving only moves a conversation out of the way. Two other rules were considered. Finishing a lesson when it is archived could not be undone by restoring it, so Restore would not bring back what the learner archived. Allowing only finished conversations to be archived would leave an abandoned practice task in the sidebar for good, because a task finishes only when its attempt is submitted, and submitting work just to tidy the list would add evidence the learner never meant to give.

**Where the archive lives.** Whether a conversation is archived is kept in its own concept, [Archiving](../concepts/Archiving.md), which the application binds as `ConversationArchiving`, with the learner as its user and the GroundedTutoring session as its item. GroundedTutoring's purpose is to help a learner understand and practice a topic from sources they can inspect. Which of the learner's conversations a list shows is a different purpose, keeping the learner's workspace tidy, so an archived flag on the session would mix two concerns in one concept, and it would also need another exception to GroundedTutoring's rule that a closed session never changes, beside reopening a finished lesson. Archiving is generic, as Styling and Preferring are: it stores the learner and the session as keys and never reads or changes the session. GroundedTutoring gains only a parameter on one query, `hidden` on `_recent`, so the sidebar's order and cap still come from a single query, as the [shared reads](LearningReads.md) describe. Because archiving writes only to its own collection, and no reaction follows `archive` or `restore`, the conversation's dialogue and citations, its practice case and judgments, the mastery estimates built from them, and the plan are all left untouched.

[ArchiveConversation](reaction:Learning.ArchiveConversation) takes `studySession`.

- When the request arrives, `Sessioning.use` turns the session into the acting learner. No request field can name another learner.
- Where [OwnedSession](view:Reads.OwnedSession) holds for that learner and session, the endpoint calls `ConversationArchiving.archive` with the learner as owner and the session as item, and answers `{}`. The session may be open or closed, a lesson or a practice task. Archiving a conversation that is already archived changes nothing and keeps the time it was first archived, so a retry after a lost reply is safe.
- Where OwnedSession does not hold, because the session is unknown or belongs to another learner, the endpoint answers `SESSION_UNAVAILABLE` and changes nothing.

[RestoreConversation](reaction:Learning.RestoreConversation) has the same shape and calls `ConversationArchiving.restore` instead. Restoring a conversation that is not archived changes nothing, so a retry is safe here too.

On these two endpoints, `SESSION_UNAVAILABLE` carries its own sentence, "This conversation is not one of yours. Choose one of your own conversations.", because they accept a closed or archived conversation. Request admission declines both first with the sentence of [ConversationReady](former:Access.ConversationReady), as the [request admission](LearningAccess.md) describes.

An archived conversation is read-only because [OpenSession](view:Reads.OpenSession) leaves it out. Respond, Question, Reply, Hint, Transcript, FinishLesson, and Assess therefore refuse it as they refuse a closed session, and Continue no longer lists it. ReopenableLesson leaves it out too, so ReopenLesson refuses an archived finished lesson until it is restored. Read still returns it, and names it in `archived`, so the lesson page shows it without its message box and without the buttons that act on the conversation, and offers "Restore conversation" in their place. When that Restore is refused, the page reads the conversation again and the sidebar reads its lists again, as after a refused Continue. RetryAssessment, Correct, and Regrade act on a submitted attempt's case rather than on the conversation, so they keep their own rules.

## Assessment

[Assess](reaction:Learning.Assess) requires the learner to review the complete attempt and declare freshness and outside help. Confirmation triggers submission and closure. The endpoint waits for those actions, asks the provider to judge the saved original work, rechecks the session, and records the judgment. It waits for the resulting progress reactions before responding. A provider failure leaves a closed, unjudged case. When the session is not one of the learner's open sessions, Assess answers `SESSION_UNAVAILABLE` before confirming anything. [RetryAssessment](reaction:Learning.RetryAssessment) grades that saved case without changing its work, date, criteria, or identity. Its session is already closed, so RetryAssessment answers `SESSION_UNAVAILABLE` only when the session is not one of the learner's own. The UI reads completed judgments instead of submitting them again.

[Correct](reaction:Learning.Correct) appends a manual revision based on the judgment the learner saw. It accepts a practice case or an [imported case](Importing.md). An imported case keeps gateMet false. When [OwnedAnyCase](view:Reads.OwnedAnyCase) shows that the case is the learner's own imported case and the correction sets gateMet true, Correct answers `IMPORTED_GATE_UNAVAILABLE` and changes nothing: imported coursework cannot show the complete demonstration gate. A correction of the learner's own imported case with gateMet false, or of the learner's own practice case, goes to `AssessmentReviewing.revise` with origin MANUAL, which still refuses an outdated judgment. When OwnedAnyCase does not hold, because the case is unknown or belongs to another learner, Correct answers `REVISION_CASE_UNAVAILABLE` with the concept's sentence and does not call `revise`.

## Refusal sentences

Each of these refusals reaches the learner with one sentence, which the host adds as `detail`, as the [runtime contract](../runtime.md) describes:

- `SESSION_UNAVAILABLE`, from Respond, Question, Reply, Hint, Transcript, FinishLesson, Assess, and RetryAssessment: "This session is closed, archived, or not one of yours. Choose one of your open sessions." From ArchiveConversation and RestoreConversation: "This conversation is not one of yours. Choose one of your own conversations." From ReopenLesson, which accepts only a finished lesson: "This session is still open, archived, a practice task, or not one of yours. Choose one of your finished lessons to continue."
- `SESSION_CHANGED`, from Question, Reply, and Hint when the session closes while the tutor answers: "This session closed before the tutor's answer could be saved. Your own work in it is still saved."
- `SKILL_CHANGED`, from Task when the skill's requirements change, or the skill stops being one of the learner's confirmed skills, while the tutor answers: "This skill changed while the tutor was answering, so nothing was saved. Try again."
- `MATERIAL_UNAVAILABLE`, from Suggest, and from the material read and the skill endpoints of the [course composition](Courses.md): "This material is not available in this course. Reload the page to see its materials."
- `WORK_MATERIAL_NOT_SOURCE`, from Suggest, and from ProposeSkill, EditDraft, and AddSkillSource in the [course composition](Courses.md#the-learners-own-work), for the learner's own work: "This file is your own work, which the tutor reads as evidence of your attempt, not as a teaching source. Choose one of the course's materials instead."

## Adjusting the estimate

[Adjust](reaction:Learning.Adjust) lets the learner set the estimate by hand with a reason. The skill page offers it beside the estimate as "Adjust estimate", apart from "Review or correct this assessment". The request carries `skill`, `adjustmentKey`, `value`, and `reason`. The page makes a new key, such as a random UUID, for each new adjustment. It keeps that key with the value and reason in the browser's session storage until it gets an answer, as the draft queue in the [course composition](Courses.md) does, so a retry sends the same key and input even after a reload. Changing the value or reason starts a new adjustment with a new key.

- When the request arrives, `Sessioning.use` turns the session into the acting learner. No request field can name another learner.
- Where [ActiveSkill](view:Reads.ActiveSkill) holds for that learner and skill, it gives the skill's current definition. The endpoint then calls `MasteryEstimating.adjust` with the learner, the skill as subject, that definition, `adjustmentKey`, `value`, and `reason`. It waits for the adjustment and for the replan below to settle, then answers with the `adjustment` identity. The page then calls Read again, which shows the adjustment with its reason in the timeline, and the new estimate.
- Where ActiveSkill does not hold, the endpoint answers `SKILL_UNAVAILABLE` with the detail "Choose one of your confirmed skills before adjusting its estimate." and changes nothing. An unknown skill, another learner's skill, and a draft skill get this same answer.
- Where ActiveSkill holds, the concept decides the remaining refusals and their messages. `INVALID_ADJUSTMENT_KEY` means the key is blank. `ADJUSTMENT_KEY_CONFLICT` means the key was already used for a different skill, value, or reason. `ADJUSTMENT_TRACK_UNAVAILABLE` means the current definition has no starting estimate yet. `INVALID_MASTERY_ADJUSTMENT` means the value is not a number from 0 through 100 or the reason is blank. Each refusal reaches the learner with the concept's message and leaves every concept unchanged.

Through HTTP and the runtime gateway, request admission checks the same ActiveSkill condition before dispatch. It declines an unknown skill, another learner's skill, and a draft skill alike, with the admission layer's decline code and the same detail as `SKILL_UNAVAILABLE`. A caller therefore cannot tell the three cases apart on either path. The endpoint repeats the check for a skill that changes after admission and for callers that bypass admission. Admission does not check the key, value, or reason, so those refusals keep the concept's message.

Each new key appends one adjustment for the current definition; tracks for earlier definitions are never adjusted here. A repeated request with the same key and input returns the same adjustment and changes nothing in MasteryEstimating, so a retry after a lost reply never adds a second row.

An adjustment never makes a skill ready by itself. The concept's readiness rule decides readiness, and the page shows the concept's own readiness sentence.

[ReplanAfterAdjustment](reaction:Learning.ReplanAfterAdjustment) proposes new reviews after an adjustment, the same way ReplanAfterEvidence does after evidence in the [progress reactions](Progress.md). It belongs to this composition so this work does not edit the progress composition.

- When `MasteryEstimating.adjust` succeeds for a learner and skill, it waits for ordinary work in that flow to settle.
- Where [OwnedSkill](view:Reads.OwnedSkill) gives the skill's course, [CanReplan](view:Reads.CanReplan) holds for the learner and that course, [ActivityInProgress](view:Planning.ActivityInProgress) does not hold for the learner, and [PlanContext](view:Reads.PlanContext) gives the review candidates, horizon end, explanation, and fingerprint,
- then it calls `StudyPlanning.replan` with the learner, the course as scope, those values, and `workloadComplete` false.

Planning sees adjustments because the tracks PlanContext reads now list each track's adjustments. The intended effect of this replan is:

- The adjusted skill gets a review candidate whose priority comes from the adjusted estimate, when its next review falls within the seven-day horizon that planRequest uses. A lowered estimate moves that review ahead when the daily budget is short, and a raised one moves it back.
- After an independent success, the review starts on the review day of the due instant the adjustment moved, as [Shared learning reads](LearningReads.md), "The review day", describes. An adjustment changes neither the memory's stability nor its difficulty, but the estimate's forgetting restarts from it, so the memory is due one stability after the adjustment, and the Memory view names that same day. After a slip, a gap, or supported work, the review still starts the next calendar day after that result. An activity already finished for that evidence within its window is not offered again, because finishing an activity records time, not evidence.
- The fingerprint includes adjustments, so a proposal made before the adjustment can no longer be activated as current. ActivateRoutine activates the new proposal when nothing else blocks it.

[planRequest](computation:planRequest) states how candidate keys and the fingerprint carry adjustments.

When CanReplan does not hold, because the course has no saved budget or an activity is in progress in it, no proposal is made. When an activity is in progress in another course, ActivityInProgress holds and no proposal is made either, because the planning concept would refuse it; finishing or stopping that activity refreshes this course. Neither case is a failure, and the Adjust endpoint answers with the saved adjustment. The Adjust endpoint waits for this reaction before answering. If the replan is refused or faults, the answer is that failure: the planning concept's refusal message, or the general internal error. The adjustment stays saved, because one concept's write is not rolled back when another concept fails. The answer cannot say which step failed, so after any failed or lost reply the page:

- shows the failure's message, followed by "The timeline below shows whether your adjustment was saved. Sending it again will not add it twice.";
- reads the skill again, so the timeline shows whether the adjustment was saved; and
- keeps the key with the unchanged value and reason, so sending again is a retry.

A retry with the same key returns the saved adjustment without adding a row. Because `adjust` succeeds again, this reaction runs again and proposes from current state, which completes a replan that failed. Updating the plan through `/planning/propose`, or any later replan trigger, also recovers it.

## Reading a cited passage

Each citation names a material and a location in it. When the learner opens an entry under "Sources used", the page calls the existing `/courses/materials/read` endpoint from the [course composition](Courses.md) with the citation's material. That read checks the session, the material's owner, and the course owner, and refuses with `MATERIAL_UNAVAILABLE` or `COURSE_UNAVAILABLE`. It returns the title, locator, readable content, and retained files. Each retained file lists its renditions, and each rendition has a location, as the [material data](../material-data.md) describes.

The page shows every rendition whose location equals the citation's location, in saved order: a text rendition as its text, and an image rendition as the image. The importer gives an uploaded image one location, and citations use the importer's locations, so a citation into an image names that location and matches its rendition; the material data defines no finer image-region locations today. If no rendition matches, the page shows the material's readable content and names the location. It labels the passage with the material title and location, as the source labels do today. If the read refuses, the page shows that reason in place of the passage.

An image rendition holds a retained file reference, not the image itself. The page loads the image through the host's existing material-file download, which is a host route rather than an endpoint. As the material data requires, that download first checks the signed-in learner's access to the material and the exact file reference, then reads the bytes. The file store keeps each learner's files under a digest of that learner's identity, so another learner's reference cannot be read.

No new endpoint is needed. The existing read returns every location and file reference, and the existing download serves the image with the same session and ownership checks. A citation can only name materials the session uses, and those belong to the session's learner and course. Saved materials never change, so a cited location stays valid.

## Listening

Listening to lessons, practice questions, tutor replies, and hints is screen-only. The browser speaks text that Read already returns, so it needs no endpoint or contract. Formulas are read as words where the form is common, such as "x squared" for `x^2` and "a over b" for `\frac{a}{b}`, and otherwise as their source without the delimiters. An interactive example in a lesson answer is not read out; Listen says "There is an interactive example here:" and the example's title.

## Interactive examples

A learner who turns on interactive examples in [Settings](Settings.md#interactive-examples) may find one interactive example in a lesson answer: a slider over a formula, a small table, steps revealed one at a time, or a question with a few options. An example is the tutor's illustration of a passage, not a quotation and not evidence, so it points at the passage it illustrates, and the host checks it exactly as it checks a citation. This is an experiment, and it is off by default. A learner who leaves it off sends the tutor exactly the request it received before examples existed, and gets the same answers.

**Which answers.** Only a lesson's opening explanation and a lesson's replies can hold an example. [Reply](reaction:Learning.Reply) and [Question](reaction:Learning.Question) read the learner's answer style through [AppliedAnswerStyle](view:Settings.AppliedAnswerStyle) when they prepare the request, and [withAnswerStyle](computation:withAnswerStyle) marks the request only when the style is `interactive`. A marked request's instruction ends with one more paragraph. It allows at most one example and only when it helps, describes the four kinds and their limits, asks for plain text with Unicode symbols inside the example, and reminds the tutor that the example is an illustration, so the answer's citations still name the passages its text relies on. Practice tasks, hints, grading, skill suggestions, and graded-work extraction never ask for an example, so practice and assessment work as before.

**The format.** An example is a fenced code block in the answer's Markdown: a line of three backticks with the info string `stillgotit-widget`, one JSON object, and a closing line of three backticks. The object's `kind` is one of four, and every kind has `source`, a material and a location in the shape of a citation.

- `slider`: a `title`, a `formula` in one or two variables, the `variables`, each with a `name`, a `label`, `min`, `max`, `step`, and a starting `value`, and an `output` label. The learner moves one slider for each variable and sees the formula's value. A formula holds numbers, the variables, `+ - * / ^`, parentheses, `pi` and `e`, and the functions sqrt, abs, exp, ln, log (base 10), sin, cos, tan, asin, acos, atan, floor, ceil, round, min, and max. A small evaluator in [src/widget-formula.ts](../../src/widget-formula.ts) reads the formula into a tree and works out its value by walking the tree, so nothing the tutor writes is ever run as code. Each variable is used by the formula, its range holds at most 1,000 positions, and the formula must have a value at the starting values.
- `table`: a `caption`, the `columns`, and the `rows`, at most 6 columns and 8 rows of short strings or numbers. A cell may be empty.
- `steps`: a `title` and 2 to 8 `steps`, which the learner reveals one at a time.
- `choice`: a `question`, 2 to 5 different `options`, the `answer`, which is exactly the text of the one correct option, and a one-sentence `explanation` that appears after the learner picks.

Strings are plain text. A title, caption, or question has at most 160 characters, a label, column heading, or cell at most 80, an option 160, a step 300, and the explanation 400, and one block's JSON at most 4,000. A string may not hold a backslash or a control character, because either means the tutor wrote LaTeX, whose escapes JSON reads as other characters.

**How the host checks it.** The host checks the examples of every lesson answer in [the answer validation](../../src/host/tutor-generation.ts), right after the citations, whatever the learner's style. Each block must be closed, hold JSON that reads as one of the four kinds within the limits, and name in `source` one of the lesson's materials at a location the citation check accepts: `content` when the material has text, or one of its rendition locations. The learner's own attached work is never a source. Only the first block that passes is kept, rewritten in a canonical form with its known fields only. A block that fails, and any block after a kept one, is dropped from the answer, and the server log gets one line that names the reason, such as "Tutor answer example dropped: its source does not name one of the lesson's materials at a valid location.", with nothing from the answer, the learner, or the material. The rest of the answer is kept, so a bad example never costs the learner the answer. Only an answer whose text is nothing but failed examples is refused, like any other incomplete answer. The page uses the same module to find blocks, [src/answer-widgets.ts](../../src/answer-widgets.ts), so it shows exactly the blocks the host checked. No concept changes: GroundedTutoring saves the answer's text with the example inside it, as it saves any text.

**On the lesson page.** The page renders the answer's Markdown as before and shows each example in place of its block, as a card inside the answer. The card has an "Illustration" label, the example's title, an ⓘ that says the example is the tutor's own illustration and is not saved, and, below the example, the same "From <source> ↗" chip that the citations use, which opens the passage.

- A slider has one range input for each variable, with its value beside it, then the formula's result, which screen readers hear as it changes, and the formula itself. "Back to the starting values" appears once a slider has moved, and using it returns the focus to the first slider.
- A table has a header row, and on a narrow screen it scrolls sideways inside its own frame, which the keyboard can reach.
- Steps start with the first step. "Show next step" reveals the next one, "Show all" the rest, and "Start over" returns to the first. Under reduced motion, every step shows at once, without the buttons.
- A choice shows its options as buttons. Picking one says whether it was right, marks the correct option and the learner's pick in words as well as color, and shows the explanation; "Try again" clears the pick. A choice stays on the page: it calls no endpoint, saves nothing, is not evidence, and leaves the estimate unchanged.

Everything in an example is reached and used with the keyboard, and both themes use the app's color tokens. Copy writes an example out as plain text, and Listen says "There is an interactive example here:" and its title, so neither gives the learner raw JSON. How the page shows an example does not depend on the learner's style, so a learner who turns examples off still sees the examples in conversations they already have. Only lesson answers show examples. A block in any other text, which the tutor is never asked for, shows as an ordinary code block.

## Suggestions and ordering

[Regrade](reaction:Learning.Regrade) first saves the learner's clarification, requests another judgment of the original work, and appends a revision only if the expected judgment is still current. It needs the practice task that produced the work. When OwnedAnyCase shows that the case is the learner's own imported case, Regrade answers `REGRADE_IMPORTED_UNAVAILABLE` before saving a clarification or contacting the tutor: imported coursework has no practice task to regrade, so correct it manually instead. When OwnedAnyCase does not hold, Regrade answers `REVISION_CASE_UNAVAILABLE`, as Correct does. Correct and Regrade use the same evidence and planning reactions.

OwnedAnyCase joins a practice or imported case to its author and course without reading a task. It answers the case's skill, course, requirements version, and imported flag. The existing [OwnedCase](view:Reads.OwnedCase) binds the case's practice task, so it never holds for an imported case. Regrade keeps OwnedCase for its practice-case path. Correct, Regrade's imported-case refusal, and their shared admission use OwnedAnyCase.

[Suggest](reaction:Learning.Suggest) requests editable skill suggestions from an owned course source. The graded-work check applies only after the material is confirmed as the learner's own in a course they own. For such a material with a [graded title](computation:gradedTitle), Suggest answers `GRADED_MATERIAL_NOT_SOURCE` before contacting the tutor: graded work is evidence, not a teaching source. For the learner's own work it answers `WORK_MATERIAL_NOT_SOURCE` before contacting the tutor, for the same reason. Over HTTP, request admission declines the learner's work first with "Choose a source from your own course.", because SuggestionReady admits only a source, and the page offers no Find skills for it. Any other material keeps the existing admission refusal, whatever its title, so the check never reveals another learner's material. A caller that skips admission gets `MATERIAL_UNAVAILABLE` for a material that is not the learner's own and `COURSE_UNAVAILABLE` for the learner's material in a course they do not own, the same answers as the material read in the [course composition](Courses.md). The learner must still save and confirm the selected skills.

Every flow that asks the tutor uses the learner's [tutor choice](Settings.md). Task, Question, Reply, Hint, Assess, RetryAssessment, Regrade, and Suggest read [TutorStatus](view:Settings.TutorStatus) in the condition that prepares the request and require status SAVED or DEFAULT. [withChoice](computation:withChoice) adds that model and thinking level to the prepared request, so `TutorGenerating.generate` sends exactly the validated pair and never a value from the browser. These conditions are stated once, by a helper in the settings composition that the learning and importing flows share. Question, Hint, Assess, and Regrade read the choice in the later step that asks the tutor. Before any of their writes, admission declines a saved choice that is no longer offered through [TutorReady](former:Settings.TutorReady). Each successful response also returns `tutor`, the model and level that produced the answer, which [requestChoice](computation:requestChoice) reads from the sent request; it is not stored. When Google's refusal identifies the chosen model or level, the request ends with a sentence that tells the learner to choose another one. Other refusals keep their current sentences, and the server never retries with a different model. Reply, RetryAssessment, and a new hint request then recover as they do after any provider failure. A repeated Regrade appends its clarification again, as any repeated Regrade does.

The host serializes each learner's changes, and the skill read with its repairs, because the app runs as a single process. Requests that only read do not wait for them. Conditions observe state; the concepts enforce their own atomic constraints. Source-version checks are repeated after slow provider work. Failed causal work is reported rather than presenting an incomplete response as success.

Each provider request sends its owned sources in the form the tutor reads best, as the [materials composition](Materials.md) describes. Text, recording transcripts, and every file's locations go as text. An original PDF or image goes inline when it is 15 MB or less and the request's inline files stay within 30 MB, and goes by Files API reference otherwise. A file that cannot reach the provider fails the request with its own explanation, like other provider failures, and saved work stays available.

## Tutor request kinds

Every Generating request has one kind. The composition prepares it from declared reads. The host sends it to the tutor and checks the answer before `TutorGenerating.generate` returns. Each request carries at least one source, and every source must belong to the requesting learner. If an answer breaks a rule for its kind, the host refuses the whole answer, and nothing from it is saved or shown.

Failures follow one path for every kind. For a provider failure, the host records the plain reason described in [runtime responsibilities](../runtime.md), such as a busy service, a used-up quota, a safety block, or a timeout. For a refused answer, it records "The tutor could not produce a usable answer. Try again.", and the server log keeps the refusal's reason for the app owner, without the learner or the request. Either reason ends by saying that the learner's saved work is still available. Generating then refuses `GENERATION_FAILED`, and the learner sees the recorded reason.

- **SUGGEST** sends one owned source. The answer has a unit title and one to five skills. Each skill's title, outcome, and gate is nonblank and at most 6,000 characters.
- **LESSON**, **TASK**, and **REPLY** answer with nonblank text of at most 30,000 characters and at least one citation. Each citation names a supplied material and either `content`, when that material has text, or one of its rendition locations. A TASK question must differ from every earlier task question sent with the request. A LESSON or REPLY answer may also hold one interactive example, which the host checks as [Interactive examples](#interactive-examples) describes; an example that fails is dropped instead of refusing the answer.
- **HINT** answers with nonblank text of at most 30,000 characters. It needs no citation.
- **GRADE** answers with one of the five results, a gateMet flag, and a nonblank rationale. INDEPENDENT requires saved help NONE. gateMet requires INDEPENDENT and fresh work.
- **EXTRACT** reads one graded upload for the [graded import](Importing.md), as described below.

The text of a LESSON, TASK, REPLY, HINT, or GRADE answer may carry LaTeX. Its instruction asks for mathematics between dollar signs, `$…$` inline and `$$…$$` on its own lines for a displayed equation or matrix, never as Unicode approximations or in code fences, and for no other Markdown. The lesson page renders the text as Markdown and draws each formula with KaTeX, which it loads only when a text holds a formula; a formula KaTeX cannot read shows as its source. The learner's own messages get the same formulas, and the rest of a message shows as typed. EXTRACT rows stay plain text with Unicode symbols, because the graded import shows them as written.

An EXTRACT request has exactly one source, the graded material, and no separate learner work. Graded work may be a PDF, with or without a text layer, or photos of the pages. The host sends every original of the material inline and in full, so the tutor can read handwriting and marks. Unlike the other kinds, EXTRACT never falls back to extracted text. When an original cannot be sent in full, the host refuses the request before contacting the tutor and records one of these reasons:

- A PDF larger than the inline limit (15 MB today): "This PDF is larger than 15 MB, so the tutor cannot see its marks. Upload photos of its pages instead."
- A photo that cannot be sent in full, because it is larger than that limit: "This photo is larger than 15 MB, so the tutor cannot read it. Upload a smaller photo of the page."

These reasons follow the failure path above. The learner therefore sees why the file could not be read, never a total-score message.

The context lists the course's confirmed skills in skill identity order, each with its identity, title, current outcome, and gate. The instruction tells the tutor to treat the file as data and to return one row for each question that shows its own mark, in the order the questions appear. Each row copies the question label, the mark, and the grader's feedback as written. It quotes a short excerpt of the learner's answer, proposes the listed skill the question best shows or none, proposes a result, and explains that result in one sentence. The tutor must not invent marks. It omits questions without their own mark, so work that shows only a total score yields no rows.

One extraction covers at most 50 questions. When the work has more marked questions, the instruction tells the tutor to return the first 50 in order. The import screen says that one import reads at most 50 questions and that a longer paper is split across uploads. When an answer has exactly 50 rows, the screen also warns that later questions may be missing.

The tutor answers with `rows`. The JSON schema sent with the request limits the list and the result labels, but the host still checks every rule. The host accepts the answer only when all of these hold:

- The answer is a record whose `rows` is a list of at most 50 records. An empty list is valid.
- Every row has `label`, `mark`, `feedback`, `excerpt`, `skill`, `result`, and `rationale`, and each is a string. A missing field refuses the answer. Other fields are ignored.
- `label` is nonblank and at most 100 characters. No two rows have the same label after trimming surrounding whitespace.
- `mark` is nonblank and at most 50 characters. A blank or missing mark refuses the answer.
- `feedback` is at most 2,000 characters and may be blank when the grader wrote nothing.
- `excerpt` is at most 500 characters and may be blank when the learner's answer is empty or unreadable.
- `skill` is empty, meaning no skill, or exactly one of the skill identities in the request context. An unknown skill, including a draft, archived, or other course's skill, refuses the answer.
- `result` is exactly `INDEPENDENT`, `SUPPORTED`, `SLIP`, `GAP`, or `UNCERTAIN`. Any other value refuses the answer.
- `rationale` is nonblank and at most 500 characters.

A valid answer reaches the endpoint as these rows, in the tutor's order, with each string exactly as returned. It carries no text, citations, judgment, or suggestions. Extraction happens before the learner declares help, so any of the five results is accepted here. The review step and the confirm endpoint apply the help rule.
